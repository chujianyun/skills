# 会话粘滞

多数上游支持提示词缓存（prompt cache）：同一段前缀再次出现时，命中缓存的输入按更低的缓存价格计费，首字延迟也更短。但缓存保存在单个供应商端点上，如果多轮对话的每一轮被路由到不同端点，前缀缓存就会频繁失效。

会话粘滞让同一会话的后续请求优先回到上一轮命中缓存的端点。它默认开启、无需额外配置；在请求中显式声明会话标识，可以让识别更稳定。

## 工作原理 {#how-it-works}

1. **识别会话**：从请求头、请求体字段或对话开头的内容中得到会话标识。
2. **优先回到绑定端点**：如果该会话已绑定端点，路由时它会排在同等稳定性的其他端点之前。
3. **按结果更新绑定**：请求成功后，根据本轮是否命中缓存决定绑定、续期或解绑。

会话粘滞只调整候选端点的尝试顺序，不会把请求锁死在某个端点上。绑定的端点出现故障时，请求照常切换到下一个可用端点。

## 识别会话 {#session-key}

系统按以下优先级获取会话标识：

| 优先级 | 来源 | 适用协议 |
|---|---|---|
| 1 | 请求头 `X-Session-ID` | 下方列出的全部协议 |
| 2 | 请求体 `prompt_cache_key` 字段 | OpenAI Chat Completions、OpenAI Responses |
| 3 | 自动识别对话开头的内容 | 下方列出的全部协议 |

前两种是显式声明，第三种是自动识别。两者的绑定规则略有不同，见 [绑定与失效](%E4%BC%9A%E8%AF%9D%E7%B2%98%E6%BB%9E.md#binding)。

### 显式声明 {#explicit}

为每个会话生成一个唯一值（例如 UUID），在该会话的每一轮请求中携带：

:::group

```bash title="OpenAI cURL"
curl https://tokendance.space/gateway/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer YOUR_KEY" \
  -H "X-Session-ID: 3f2b8c1e-session-001" \
  -d '{
    "model": "glm-5.1",
    "messages": [
      {"role": "system", "content": "你是一个代码审查助手。"},
      {"role": "user", "content": "帮我看看这段代码。"}
    ]
  }'
```

```bash title="Anthropic cURL"
curl https://tokendance.space/gateway/v1/messages \
  -H "Content-Type: application/json" \
  -H "x-api-key: YOUR_KEY" \
  -H "anthropic-version: 2023-06-01" \
  -H "X-Session-ID: 3f2b8c1e-session-001" \
  -d '{
    "model": "glm-5.1",
    "max_tokens": 1024,
    "system": "你是一个代码审查助手。",
    "messages": [{"role": "user", "content": "帮我看看这段代码。"}]
  }'
```

```python title="Python (OpenAI)"
from openai import OpenAI

client = OpenAI(
    api_key="YOUR_KEY",
    base_url="https://tokendance.space/gateway/v1"
)

response = client.chat.completions.create(
    model="glm-5.1",
    # 也可以改用 extra_headers={"X-Session-ID": "3f2b8c1e-session-001"}
    extra_body={"prompt_cache_key": "3f2b8c1e-session-001"},
    messages=[
        {"role": "system", "content": "你是一个代码审查助手。"},
        {"role": "user", "content": "帮我看看这段代码。"}
    ]
)
print(response.choices[0].message.content)
```

```python title="Python (Anthropic)"
import anthropic

client = anthropic.Anthropic(
    api_key="YOUR_KEY",
    base_url="https://tokendance.space/gateway"
)

response = client.messages.create(
    model="glm-5.1",
    max_tokens=1024,
    extra_headers={"X-Session-ID": "3f2b8c1e-session-001"},
    system="你是一个代码审查助手。",
    messages=[{"role": "user", "content": "帮我看看这段代码。"}]
)
print(response.content[0].text)
```

:::

::: note
会话标识只用于平台内部路由，不需要与上游供应商的任何 ID 对应。同一个值不要在不同会话之间复用，否则这些会话会共用一份绑定。
:::

### 自动识别 {#implicit}

未显式声明时，系统取对话开头的系统提示和第一条非系统消息作为会话特征。多轮对话中客户端每轮都会原样重发这两部分，所以同一会话的各轮能被识别为同一会话。

| 协议 | 参与识别的字段 |
|---|---|
| OpenAI Chat Completions | `messages` 中第一条 `system` / `developer` 消息 + 第一条其他消息 |
| OpenAI Responses | `instructions`（缺省时取 `input` 中的第一条系统消息）+ `input` 中的第一条消息 |
| Anthropic Messages | `system` + `messages` 的第一条 |
| Gemini generateContent | `systemInstruction` + `contents` 的第一条 |

自动识别按原始内容比较，以下情况会导致无法识别为同一会话：

- 系统提示或第一条消息中含有每轮变化的内容，例如当前时间、随机 ID；
- 客户端会截断或改写早期历史消息，导致第一条消息发生变化；
- OpenAI Responses 请求使用 `previous_response_id` 引用上一轮，而不重发历史（此时请求中没有稳定的对话开头）。

遇到这些情况时，请改用 [显式声明](%E4%BC%9A%E8%AF%9D%E7%B2%98%E6%BB%9E.md#explicit)。

## 绑定与失效 {#binding}

请求成功后，系统根据本轮实际服务的端点和是否命中缓存（响应用量中缓存读取的 token 数大于 0）更新绑定：

| 场景 | 结果 |
|---|---|
| 显式声明的会话，请求成功 | 绑定到本轮服务的端点 |
| 自动识别的会话，本轮命中缓存 | 绑定到本轮服务的端点 |
| 自动识别的会话，本轮未命中缓存 | 不写入绑定 |
| 请求落在已绑定端点，命中缓存 | 续期 |
| 请求落在已绑定端点，未命中缓存 | 解绑，下一轮按默认路由重新选择 |
| 已绑定端点故障，请求切换到其他端点并命中缓存 | 改绑到新端点 |
| 已绑定端点故障，请求切换到其他端点且未命中缓存 | 保留原绑定 |

绑定有效期为 **10 分钟**，每次绑定或续期都会重新计时，与主流上游缓存的保留时长处于同一量级。会话空闲超过 10 分钟后，下一轮按默认路由选择端点。

已绑定端点「应答但未命中缓存」通常说明缓存已被上游淘汰，此时继续停留在该端点已没有收益，因此系统会立即解绑，避免会话长期停留在价格更高的端点上。

::: note
绑定按「用户 + 主模型 + 会话标识」隔离。同一用户用相同的对话内容同时调用多个模型（例如批量评测）时，各模型的绑定互不影响；不同用户之间不会共享绑定。
:::

## 与供应商路由的关系 {#with-provider-routing}

会话粘滞是 [默认路由](%E4%BE%9B%E5%BA%94%E5%95%86%E8%B7%AF%E7%94%B1.md#routing) 中的一个排序因素，优先级如下：

1. **稳定性**：近期出现显著故障的端点仍排在末尾，即使它是已绑定端点；
2. **会话粘滞**：已绑定端点排在其他稳定端点之前；
3. **价格**：其余端点按价格从低到高排序。

请求中通过 `provider` 字段显式声明的偏好优先于会话粘滞：

| 字段 | 与会话粘滞的关系 |
|---|---|
| `order` | `order` 中的供应商先于已绑定端点尝试 |
| `only` | 仅当已绑定端点在 `only` 范围内时，会话粘滞才生效 |
| `ignore` | 被屏蔽的端点即使已绑定也不会被尝试 |

会话粘滞只作用于主模型（`model` 字段）的候选端点，不会改变 [模型降级](%E6%A8%A1%E5%9E%8B%E9%99%8D%E7%BA%A7.md) 中 `models` 备选模型的尝试顺序。

## 计费与观测 {#billing}

会话粘滞本身不收取额外费用。命中缓存的输入按所用端点的缓存价格计费，具体价格以 [模型详情页](https://tokendance.space/models) 为准。

响应中不会单独标注本次请求是否走了会话粘滞。可以通过响应用量中的缓存读取字段，或 [调用日志](https://tokendance.space/activity) 请求详情中的「缓存命中」判断缓存是否命中：

| 协议 | 缓存读取字段 |
|---|---|
| OpenAI Chat Completions | `usage.prompt_tokens_details.cached_tokens` |
| OpenAI Responses | `usage.input_tokens_details.cached_tokens` |
| Anthropic Messages | `usage.cache_read_input_tokens` |
| Gemini generateContent | `usageMetadata.cachedContentTokenCount` |

## 限制 {#limitations}

- **仅支持对话协议**：OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Gemini generateContent。向量、图像、视频、语音等协议不参与会话粘滞。
- **OpenAI Responses 协议的 `previous_response_id` 不保证生效**：会话粘滞只调整尝试顺序，不保证状态连续；即使显式声明了会话标识，绑定端点故障或解绑后，请求仍可能落到其他端点，上游通常会因找不到该响应而报错。需要可靠的多轮状态时，任选其一：
  - 用 `provider.only` 把请求限定到单一供应商；
  - 不使用 `previous_response_id`，在 `input` 中完整携带历史消息。
- **显式缓存的首轮**：使用 Anthropic `cache_control` 等显式缓存时，首轮只写入缓存、不会读取，自动识别的会话在首轮不会绑定；第二轮由默认路由选择端点，通常仍是同一端点，但不作保证。需要稳定回到同一端点时，请显式声明会话标识。

## 使用建议 {#best-practices}

- **多轮对话和 Agent 场景显式声明会话**：每个会话生成一个唯一的 `X-Session-ID`，在整个会话中保持不变。
- **保持对话开头稳定**：把时间、用户状态等动态内容放到消息末尾，而不是系统提示里。这既有利于自动识别会话，也能提高上游缓存的命中率。
- **单轮请求无需处理**：自动识别的会话只在命中缓存后才会绑定，单轮请求不会受到影响。
