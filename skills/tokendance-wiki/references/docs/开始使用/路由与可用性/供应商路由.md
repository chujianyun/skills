# 供应商路由

词元跳动为同一模型配置了多个供应商端点。系统会根据各端点的实时表现智能选择最优端点，并在供应商不可用时自动切换，整个过程对调用方完全透明。

如果你希望对路由顺序有更精确的控制（例如优先使用某个供应商、屏蔽某些供应商），可以在请求体里通过 `provider` 字段显式声明偏好。

::: note
下文的 `provider.order` 等字段需要填入"供应商标记"——它是每个供应商的短标识（例如 `deepseek`、`moonshot`、`zhipu`）。在 [模型详情页](https://tokendance.space/models) 把鼠标移到供应商名称上即会出现复制按钮，点击就能拿到对应的标记。
:::

## 默认路由（价格优先） {#routing}

当请求未带 `provider` 字段时，系统按以下顺序对候选端点排序，依次尝试直到请求成功：

1. **稳定性过滤**：近期出现显著故障的端点会被降级到候选列表末尾，仅在其他端点全部失败时才会作为兜底尝试。
2. **会话粘滞**：多轮对话中，上一轮命中缓存的端点排在其他稳定端点之前，详见 [会话粘滞](%E4%BC%9A%E8%AF%9D%E7%B2%98%E6%BB%9E.md)。
3. **价格优先**：在稳定端点中，按价格从低到高排序。价格相同时结合其他因素（延迟、可用性）进一步排序。
4. **自动回归**：被降级的端点在恢复稳定后自动回到正常顺序，无需人工干预。

::: note
价格以请求当前协议下各计费项的平均费率估算。不同协议下同一端点的价格可能不同（例如某些端点对 Anthropic 协议单独计费），系统会使用当前请求协议对应的价格参与排序。
:::

## 显式控制路由 {#provider-preferences}

在请求体顶层加一个 `provider` 对象即可声明偏好。所有字段都是可选的，可单独或组合使用。

```json title="请求示例"
{
  "model": "deepseek/deepseek-v3.2",
  "messages": [{"role": "user", "content": "你好"}],
  "provider": {
    "order": ["deepseek", "moonshot"],
    "only": ["deepseek", "moonshot", "zhipu"],
    "ignore": ["beta-provider"],
    "allow_fallbacks": true
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| order | string[] | 优先尝试的供应商列表，按数组顺序逐一尝试 |
| only | string[] | 只允许使用此列表中的供应商 |
| ignore | string[] | 不使用此列表中的供应商 |
| allow_fallbacks | boolean | 默认 true。设为 false 时，order / only 中没命中的端点不会再被尝试 |

### order：声明优先顺序 {#order}

按数组顺序逐个尝试。例如下面的请求会先试 `deepseek`，失败后再试 `moonshot`，再失败则按默认策略继续向后兜底。

```json
{
  "provider": {
    "order": ["deepseek", "moonshot"]
  }
}
```

若同时设置 `allow_fallbacks: false`，则 order 之外的供应商不会再被尝试，全部失败时直接返回错误。

### only：限定可用范围 {#only}

只允许在白名单内的供应商之间路由。常见用途：合规约束（仅允许某些供应商）、成本控制（仅允许某些低价供应商）。

```json
{
  "provider": {
    "only": ["deepseek", "zhipu"]
  }
}
```

### ignore：屏蔽特定供应商 {#ignore}

从候选列表中移除指定供应商。例如临时回避某个不稳定的端点：

```json
{
  "provider": {
    "ignore": ["moonshot"]
  }
}
```

ignore 与 only 可以同时使用，最终生效的是 only 范围内、不在 ignore 列表中的端点交集。

### allow_fallbacks：是否允许兜底 {#allow-fallbacks}

默认 `true`，表示当 order / only 中的端点全部失败后，仍会按默认策略尝试其他可用端点。设为 `false` 时严格仅在指定范围内路由：

```json
{
  "provider": {
    "order": ["deepseek"],
    "allow_fallbacks": false
  }
}
```

上面的请求只会尝试 `deepseek`，失败后立刻返回错误，不会去试其他供应商。

::: warning
`order / only / ignore` 中提供的标记必须真实存在，否则请求会以 **400 BadRequest** 拒绝，而不是静默忽略未知值。这能避免拼写错误带来的意外路由。
:::

## 自动容错 {#failover}

当选中的端点返回服务端错误（5xx）或限流（429）时，系统会自动重试下一个可用端点，直到请求成功或所有候选端点都已尝试。400 类客户端错误不会触发重试。

以下两种情况会影响容错能力：

### 流式请求 {#streaming}

如果端点在开始返回数据之前就失败了，系统可以无感地切换到下一个端点。但一旦数据已经开始发送给客户端，就无法再切换端点，错误会直接透传给客户端。

::: note
建议在客户端实现流式请求的错误处理逻辑，以应对流中断的情况。
:::

### 协议不一致 {#protocol-constraint}

容错能力取决于该模型在**当前请求协议**下有多少个可用端点，而非供应商总数。例如一个模型有两个供应商，但只有一个支持 Anthropic 协议，那么通过 Anthropic 协议请求时将无法容错。

::: tip
如果需要容错保障，建议使用模型支持最广泛的协议（通常是 OpenAI 协议），或结合 [模型降级](%E6%A8%A1%E5%9E%8B%E9%99%8D%E7%BA%A7.md) 配置备选模型。
:::
