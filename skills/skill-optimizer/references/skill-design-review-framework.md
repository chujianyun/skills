# Skill 设计评审框架

用于决定如何取舍指令、调整自由度与组织资源。局部修订只看相关部分；模式分析有助于解释问题时才使用。

## 方法来源与适用范围

融合既有的 Anthropic 技能编写经验、Tool Wrapper / Generator / Reviewer / Inversion / Pipeline 设计视角，以及 OpenAI 的 [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)（2026-09-11）。

OpenAI 文章主张缩短并收窄触发描述、按需读取资料、重新审视过细流程与确认边界，并明确完成条件。它也提醒共享技能可能由不同模型使用。这些是重新评估旧规则的理由，不是删除保障或固定模型专属行为的依据。

下列审查方法是本技能的落地设计，不代表来源文章要求使用这些表格或固定评测。平台限制、安装命令等易变事实需要时再查对应官方文档；无需每次审查重新浏览全部来源。

## 一、先判断增量价值

以目标行为为起点：用户需要什么产物，模型缺少什么领域知识，哪些失败需要防止，何时算完成？不要从“一个标准技能应有多少文件”倒推设计。

| 指令内容 | 通常如何处理 | 保留或调整依据 |
|---|---|---|
| 任务特有知识、工具限制、真实故障经验 | 保留并写明适用条件 | 删除会损害正确性或稳定性 |
| 权限边界、不可逆操作、必须遵循的业务顺序 | 保留硬约束 | 必须有具体操作对象和影响 |
| 成熟的常用做法 | 作为默认建议 | 允许根据输入和环境选择更合适的方法 |
| 通用常识、重复说明、没有任务价值的劝告 | 合并或删除 | 能说明为何不会损失保障 |
| 只在部分场景有用的细节 | 条件化或按需加载 | 根文档可以直接定位，不要求每次读取 |
| 为旧模型失败添加的补丁 | 先检查证据与现用模型 | 未验证前不假定已失效 |

Gotchas 应有高信息价值。随着使用积累也要淘汰失效或重复条目，避免只增不减。一次失败不自动升级为永久硬规则；先判断它是否有复现条件。

## 二、选择合适的自由度

- **硬约束**：安全、授权、格式兼容、业务不变量和必要依赖顺序。明确违规后果及停止条件。
- **默认做法**：经过验证的常见路径。说明适用条件和可接受替代方式。
- **自主方法**：不会影响契约的资料定位、分析组织、措辞或实现选择。给出目标和判断标准即可。

例如，对复杂发布保留必要顺序；对一句 description 的调整不强制完整模式分析、多轮提问和全仓库测试。仓库明确要求的检查仍需执行。

在授权边界内写清“继续做到哪里”：修改、必要验证、修复本次问题和已授权的交付动作。暂停应对应具体输入缺失、授权缺失或无法解决的失败；不要把每个阶段都变成用户审批点。

## 三、按任务组织上下文

把名称和描述视为路由入口，优先保证短描述能独立区分任务。将工作流细节留在正文，避免为了覆盖关键词而吸引所有相邻请求。

资源入口说明“遇到什么问题读什么”，评估一次真实请求会加载哪些文件。根文档很短但无条件读取所有 references，仍然浪费上下文。反之，单文件已经清楚时无需为形式拆分。

README 服务于人类使用者，是否新增取决于需求和仓库规定。索引解决定位困难，脚本解决重复且可确定的操作，模板解决必要的输出一致性；都需要具体用途。配置、日志、历史和记忆同样按需求评估，敏感状态不写进可分发的技能本体。

## 四、用模式解释问题，而非强制套型

| 模式 | 主要价值 | 值得检查的缺陷 | 可能的过度约束 |
|---|---|---|---|
| Tool Wrapper | 提供特定工具或领域知识 | 触发过宽、缺少工具陷阱、依赖不明 | 每次读取全部工具文档 |
| Generator | 稳定生成所需产物 | 输出要求不清、必要模板缺失 | 所有请求都套同一长模板 |
| Reviewer | 找出有证据的问题 | 没有判断依据、遗漏关键风险 | 每次穷举所有维度、为改而改 |
| Inversion | 收集不可缺少的输入 | 在关键未知项上擅自假设 | 上下文已有答案仍逐项提问 |
| Pipeline | 保证存在依赖的操作顺序 | 跳过必要检查、失败后继续危险步骤 | 将可自主完成的阶段都设为审批点 |

允许主次模式组合，也允许省略模式标签。是否保留一个步骤取决于任务依赖和保障价值，不能仅用模式名称证明其必要性。

技能粒度按主要职责和触发边界判断。出现混杂或重叠时才检查相关相邻技能；实际父目录可以是分类目录，不以是否叫 skills 作为判断条件。合并、删除或跨技能改动需另行核实授权。

## 五、跨模型与证据

先了解技能的使用环境；未知时保留通用而明确的约束。必要的示例和领域步骤可能对不同模型都有帮助，不将“模型更强”当成自动删减依据，也不默认某个模型需要固定的繁复流程。

修改后按影响选择代表场景；实际使用多个模型且变更可能影响它们时，选择有代表性的模型进行验证。没有环境时列出待验证项，不虚构兼容性结论，不自动发起额外付费调用。

区分三种证据：文件检查能支持结构正确，场景推演能发现逻辑冲突，真实运行才能支持实际行为判断。需要比较效果时控制模型和环境等条件。测试通过后完成收尾；只有新失败或未解决的问题才扩大验证。

## 六、适度输出

轻量审查通常只需找出最值得处理的一到三个问题，写清依据、拟改文件和验证方式；没有有效问题则保留原样。

复杂重构可以补充模式取舍、优先级、风险、依赖和范围外建议。格式服务于用户判断，不要求每次填满所有栏目。

审查完成后应能解释：每项新增为何必要，每项删减如何保留保障，哪些预期行为有验证，哪些仍只是推断。
