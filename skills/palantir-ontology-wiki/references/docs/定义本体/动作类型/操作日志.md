# 操作日志

操作日志将所有操作提交建模为可在对象感知的Foundry工具中分析和显示的对象类型。使用操作日志对象类型作为决策工作流程的输入，并监控对Ontology的更改。

:::callout{theme="neutral"}
操作日志旨在捕获通过提交操作所做的决策，并将这些决策作为数据在Ontology中提供。对于希望记录对象所有编辑的应用案例，可以为对象类型启用[编辑历史](../../%E6%9C%AC%E4%BD%93%E6%9E%B6%E6%9E%84/%E5%AF%B9%E8%B1%A1%E7%BC%96%E8%BE%91/%E5%90%AF%E7%94%A8%E7%94%A8%E6%88%B7%E7%BC%96%E8%BE%91%E5%8E%86%E5%8F%B2.md)。
:::

## 背景

操作是修改Ontology和触发相关副作用的主要方式。通常，这些Ontology的修改是特定决策的结果，或伴随有数据审核的要求。操作日志简化了代表这些决策和数据编辑的对象类型的生成和维护。为了便于识别，所有操作日志对象类型都以`[LOG]`作为前缀。

## 操作日志Ontology

操作日志对象类型与操作类型一一对应。提交一个操作会生成一个对应操作日志对象类型的新对象。这个新创建的对象会自动链接到所有被提交操作编辑的对象。通过将日志对象类型与操作类型一一建模，操作日志支持捕获超出特定对象编辑的上下文信息，例如同时编辑了哪些其他对象以及在提交操作时世界的状态（由Ontology表示）。

例如，想象一个`关闭警报`操作类型，其将许多选定的`警报`对象的“状态”属性修改为“已关闭”。当配置了操作日志时，一次关闭10个`警报`对象将产生一个`操作日志`对象，并通过外键链接到所有10个`警报`对象。

### 操作日志架构

默认情况下，操作日志对象类型存储：

* **操作 RID：** 单个操作提交的唯一标识符
* **操作类型 RID：** 单个操作类型的唯一标识符
* **操作类型版本：** 每次更新操作类型时自动递增的版本号
* **时间戳：** 操作提交的UTC时间戳
* **用户ID：** 提交操作的用户的Multipass用户ID
* **编辑对象：** 被操作编辑的所有对象的主键值。注意，不支持存储编辑对象的主键以外的属性。
* \[非必填] **摘要：** 用于描述操作的可定制字符串
* \[非必填] **参数值**
* \[非必填] **对象引用参数的属性值**（如果启用了`允许多个值`，则不支持对象引用参数）

操作日志对象类型可以配置为存储未被操作编辑的对象属性。这使您能够存储数据编辑以及关于Ontology编辑背景或动机的相关信息。

回到`关闭警报`操作类型的例子，想象`警报`对象还具有“优先级”属性，包含"高优先级"和"低优先级"的值，以及“创建于”时间戳和“来源”机器。操作日志支持存储这些属性，即使它们未被`关闭警报`编辑。通过聚合“优先级”，我们可以在不编辑列的情况下回答诸如“多数‘高优先级’警报的来源在哪里？”或“关闭‘高优先级’警报需要多长时间？”等问题。

## 基于函数的操作类型的操作日志

要为基于函数的操作类型配置操作日志，支持的Ontology编辑函数必须配置`编辑`来源。有关`编辑`来源的更多信息，请参见[函数文档](../%E5%87%BD%E6%95%B0/Ontology%20edits/%E6%A6%82%E8%BF%B0.md)。

## 操作日志时间线

您可以使用自定义Workshop微件在时间线上查看操作日志对象类型。使用此微件，可以配置时间线以支持数据审核，以帮助回答“更改了什么，由谁更改了，何时更改？”的问题。

在Workshop中，操作日志对象类型可以联合在一起，以便在应用案例或Ontology中查看编辑的整体视图。

通过选择编辑的对象类型来配置操作日志时间线。然后选择要显示的操作日志对象类型以及所需的操作日志对象类型属性。
