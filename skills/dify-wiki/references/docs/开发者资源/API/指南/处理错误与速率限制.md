# 处理错误与速率限制

> 错误响应的统一结构、各状态码类别的含义，以及哪些失败值得重试

> 本文档由 AI 自动翻译。如有任何不准确之处，请参考 [英文原版](https://docs.dify.ai/en/api-reference/guides/errors.md)。

应用和经典知识库的接口都以同一种三字段 JSON 结构返回错误：

```json theme={null}
{
  "code": "invalid_param",
  "message": "user is required",
  "status": 400
}
```

`status` 与 HTTP 状态码一致；`code` 是稳定的标识符，适合作为分支判断的依据；`message` 是供人阅读的详细信息。每个接口页面都会列出它可能返回的所有 `code`。

> [!NOTE]
>
> Agent 知识库 API 同样使用这三个字段，并会在很多错误中附带 `failure` 对象。`failure` 提供了哪些信息、何时该重试，详见其 [处理错误](API%20%E6%A6%82%E8%A7%88/%E7%9F%A5%E8%AF%86%E5%BA%93/Agent%20%E7%9F%A5%E8%AF%86%E5%BA%93%20API.md#handle-errors) 部分。

## 状态码类别速览

| 状态码 | 含义 | 典型 `code` |
| :- | :- | :- |
| 400 | 请求或应用配置无效 | `invalid_param`、`bad_request`、`app_unavailable`、供应商错误（见下文） |
| 401 | 身份验证失败或访问被拒绝 | `unauthorized` |
| 403 | 不允许执行此操作，或受到套餐限制 | `forbidden`；应用本身无法使用时，部分应用接口会改为返回 `app_not_found`、`app_abnormal_status`、`app_api_disabled` 或 `workspace_archived` |
| 404 | 资源不存在，或对该密钥或 `user` 不可见 | `not_found`；会话接口则改为返回 `conversation_not_found`、`conversation_cursor_not_found`、`conversation_variable_not_found` 或 `conversation_first_message_not_found` |
| 413 / 415 | 文件过大或类型不受支持 | `file_too_large`、`unsupported_file_type` |
| 429 | 当前请求过多，或配额已用尽 | `too_many_requests`、`rate_limit_error` |
| 500 | Dify 侧出现故障 | `internal_server_error` |

> [!NOTE]
>
> 在 Dify Cloud 上，应用 API 返回的 `401` 响应也可能表示请求被 [IP 访问控制](../../../%E4%BD%BF%E7%94%A8/%E5%8F%91%E5%B8%83/IP%20%E8%AE%BF%E9%97%AE%E6%8E%A7%E5%88%B6.md) 拦截。如果 API 密钥有效，请应用管理员检查请求的来源 IP 是否在允许范围内。

## 供应商错误是配置错误

有 4 个常见的 400 `code` 指向应用的模型配置，而不是你的请求本身：

* `provider_not_initialize`：没有有效的模型凭据
* `provider_quota_exceeded`：模型供应商自身的配额已用尽
* `model_currently_not_support`：当前不支持该模型
* `completion_request_error`：发起文本生成请求时出错

这些错误重试无济于事，需在 Dify 中修复应用的模型配置。

## 速率限制与配额

两个 429 `code` 的含义并不相同：

* `too_many_requests` 是并发上限：应用此刻的同时请求过多。退避后重试即可。
* `rate_limit_error` 是 Dify Cloud 的套餐配额（如工作流执行次数）。重试无法消除，只会随配额周期重置或套餐变更而解除。

在 Dify Cloud 上，知识库接口的套餐限制也以 `403` 返回，例如 [请求频率限制](../../../%E4%BD%BF%E7%94%A8/%E7%9F%A5%E8%AF%86%E5%BA%93/%E7%9F%A5%E8%AF%86%E5%BA%93%E8%AF%B7%E6%B1%82%E9%A2%91%E7%8E%87%E9%99%90%E5%88%B6.md)。这些响应的 `code` 为 `forbidden`。经典知识库接口在访问受限时也使用这个 `code`，因此要靠 `message` 区分两者，不要只根据 `code` 分支处理。

## 流中的错误

应用的流一旦打开，HTTP 状态码就已经是 `200`：失败会以 `error` 事件的形式到达并结束整个流。事件中的 `code` 取值与本页所列相同，按同样的规则分类处理即可。详见 [处理流式响应](%E5%A4%84%E7%90%86%E6%B5%81%E5%BC%8F%E5%93%8D%E5%BA%94.md)。

## 哪些错误值得重试

* **退避后重试**：`too_many_requests`、`500` 和网络故障。
* **不要原样重试**：参数校验错误（先修正请求）、鉴权失败，以及配额错误（配额未重置前不会消失）。
* **修正而非重试**：恢复调用返回的 `404` 意味着 `user` 不对或运行不存在。改正标识符即可。
